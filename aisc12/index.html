How much of a monitor’s job belongs in deterministic code?

Project proposal for AI Safety Camp 12, Virtual Edition 2027 — Anton Dziatkovskii, Palo Alto, California

Summary

A monitor watching an AI agent has two ways to decide that a transcript is fine: read it and judge, or check it and know. SLEIGHT-Bench (Anthropic Alignment Science; arXiv:2605.16626) shows how expensive the gap between those is. Across 40 attacks in 11 blind-spot categories, calibrated at a 1% false positive rate, the overall catch rate is 32% and 20 of the 40 attacks are never caught at all — counting subversions sit at 13%.

Two further results in that post are what make this a project rather than an observation. Each targeted prompt improves the class it aims at while degrading at least one other, so no single prompt covers everything; and the one intervention that verifies rather than judges — letting the monitor run arbitrary code — costs roughly an order of magnitude more model invocations and output tokens. The post’s own closing ask is token-efficient scaffolds and ensembling.

This project asks whether narrow deterministic tools buy most of that catch-rate at a small fraction of that price. We hold the monitor model fixed, replace general code execution with three specific tools the monitor calls instead of reasoning — an object-state tracker, an exact line-and-offset differ, an N-hop chain resolver — and measure three numbers per blind-spot class at a fixed 1% FPR: the catch-rate delta, the degradation caused in classes the tool does not target, and the token cost against the code-execution baseline.

The output is a set of inspect_ai tasks on a public dataset, so that anyone — AISI, Anthropic, or the next team — reruns the number rather than taking our word for it. The honest failure mode is that a deterministic tool buys its class only by spending false positives elsewhere, exactly as their prompts did; the same measurement shows that too, and that result is worth publishing.

The non-summary

Theory of change

Control and oversight proposals increasingly assume a monitor that catches a scheming or sandbagging agent. Whether that assumption holds is an empirical question with a number attached, and right now the published number is low and unevenly distributed across failure classes.

The load-bearing claim we want to move is narrower than “monitoring works”. It is: for a given blind-spot class, is the missing capability judgement or verification? If it is verification, the fix is cheap, auditable, and does not scale with model capability — a differ is a differ. If it is judgement, then monitoring inherits the reliability of the monitor model, and proposals resting on it inherit that too.

Either answer changes what a control protocol should be built out of. A world where two thirds of a monitor’s misses are verification failures is a world where oversight gets substantially more trustworthy for a few hundred lines of deterministic code. A world where they are judgement failures is one where the field should stop quoting monitor catch-rates without stating the FPR and the class.

The assumption I am least sure of, and want the team to attack first: that SLEIGHT-Bench’s blind-spot classes are the right cut of the space at all. If two classes turn out to be the same defect wearing different clothes, the per-class numbers mislead, and saying so is a real output.

Project plan

Everything needed for the first run is public and MIT-licensed: the dataset (safety-research/sleight-bench) and the harness (UKGovernmentBEIS/control-arena, which already depends on inspect_ai). The 1% threshold calibrates on the paired benign transcripts that ship with the dataset. No compute budget and no model training are required; the monitor is an API call.

  1. Weeks 1–2 — reproduce the baseline. Stand up the released blind-spot transcripts as inspect_ai tasks, reproduce the published prompted-monitor numbers at 1% FPR, and reproduce the code-execution arm’s cost. If we cannot reproduce them, that is the week-2 finding and we say so publicly.
  2. Weeks 3–4 — scorer integrity. Every scorer we write is shown red on a transcript we broke on purpose before its number counts. This is not ceremony: I filed the upstream defect where a multi-grader panel let a grader that failed to parse cast the deciding vote, so I know what a silently-passing scorer costs.
  3. Weeks 5–9 — the three tools. One tool per sub-team: object-state tracker (counting subversions), exact line-and-offset differ (file reuse), N-hop chain resolver (N-hops). Each is a narrow function the monitor calls, not a sandbox it programs.
  4. Weeks 10–12 — the cross-class matrix. Run every tool against every class, not only its own, so cross-class degradation is measured rather than assumed. Write up catch-rate delta, degradation and token cost per cell, at a fixed 1% FPR.

Backup plan

If the released dataset turns out to be insufficient for a fair 1% FPR calibration, the project pivots to the same measurement on control-arena’s own settings, which ship their own benign baselines. If the code-execution baseline cannot be reproduced within budget, we drop the cost comparison and keep the catch-rate and degradation axes, which do not depend on it.

If a tool turns out to be trivially perfect on its class, the interesting work moves to adversarial transcripts built to defeat it, and that becomes the deliverable instead.

Scope

Three tools, three classes, one fixed monitor model, one FPR. We are not building a general monitoring framework, not training anything, and not attempting the jailbreak and omission classes, where I do not yet have a deterministic check to propose and would rather say so than pretend.

Output

  • A public repository of inspect_ai tasks and deterministic monitor tools, MIT, runnable against the released dataset without our machines.
  • A write-up with the cross-class matrix — catch-rate delta, cross-class degradation, token cost — stated at a named FPR, published whether or not the tools win.
  • Where the tools are a clean fit, a pull request upstream into control-arena or inspect_ai, so the work lands where evaluators already are rather than in a repository nobody installs.
  • A LessWrong / Alignment Forum post at the end of the program, and the final AISC presentation.

Risks and downsides (externalities)

The main infohazard is that a public map of a monitor’s blind spots is also a map for an agent trying to get past one. I judge this net-positive but not costless: the blind spots are already published with their catch-rates, and what we add is defensive tooling rather than new attack categories. We will not publish new subversion strategies that are absent from the released dataset; if the team invents one while building adversarial transcripts, it goes to the dataset’s authors first.

The capabilities risk is low: nothing here trains or elicits a model, and a better differ does not make an agent more capable.

The risk I take most seriously is a false green light. A paper claiming “deterministic tools fix monitoring” on a scorer that never failed would be worse than no paper, because someone would build on it. That is why red-first scorer integrity is week three and not an afterthought, and why every number ships with its FPR and its class.
